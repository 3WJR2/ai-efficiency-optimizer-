# Test Generation Skill

**Version**: 1.0.0
**Purpose**: Systematic test suite generation for ≥80% coverage
**Applies To**: brahma-test-generator, code-implementer

---

## Overview

The Test Generation skill provides systematic patterns for automatically generating comprehensive test suites using TDD principles, property-based testing, and AI-powered test case generation. Achieves 80%+ coverage efficiently without wasteful over-testing.

**Key Capabilities**:
1. Coverage gap analysis and prioritization
2. Multi-strategy test generation (unit, integration, property-based, edge cases)
3. Test quality assessment (meaningful assertions, maintainability)
4. Language-specific test framework integration
5. Continuous test maintenance

---

## When to Use

Use Test Generation when:
- New code written (post-implementation)
- Coverage drops below 80%
- Edge cases not covered
- Integration paths missing tests
- Performance tests needed

Do NOT use for:
- Trivial code (simple getters/setters)
- Auto-generated code (ORMs, serialization)
- Third-party library code
- Deprecated code being phased out

### Phase 2: Test Strategy Selection

```markdown
**For each code section, select optimal strategy**:

1. **Pure Functions** (no side effects)
   - Strategy: Property-based testing
   - Tool: Hypothesis (Python), fast-check (JS), Proptest (Rust)
   - Why: Generates hundreds of test cases automatically

2. **API Endpoints**
   - Strategy: Integration testing
   - Tool: requests (Python), supertest (JS), httptest (Go)
   - Why: Tests real HTTP request/response cycle

3. **Database Operations**
   - Strategy: Integration with test DB
   - Tool: pytest-django, TestContainers
   - Why: Tests real database behavior (transactions, constraints)

4. **Business Logic**
   - Strategy: Unit testing with mocks
   - Tool: unittest.mock (Python), jest.mock (JS)
   - Why: Isolates logic from dependencies

5. **Error Handling**
   - Strategy: Exception testing
   - Why: Ensures errors are caught and handled properly

6. **Async/Concurrent Code**
   - Strategy: Concurrency testing
   - Why: Catches race conditions, deadlocks
```

**Strategy Decision Matrix**:

| Code Characteristic | Test Strategy | Priority |
|-------------------|---------------|----------|
| Pure function | Property-based | HIGH |
| API endpoint | Integration | HIGH |
| Database operation | Integration + DB | HIGH |
| Business logic | Unit + mocks | MEDIUM |
| Error path | Exception testing | HIGH |
| Async code | Async testing | MEDIUM |
| Performance critical | Performance testing | LOW |

### Phase 3: Test Case Generation

```markdown
**For each function, generate test cases**:

1. **Happy Path** (valid inputs, expected output)
2. **Edge Cases** (boundary values, empty, null, zero)
3. **Error Cases** (invalid inputs, exceptions)
4. **Performance Cases** (large inputs, timeouts)
5. **Integration Cases** (component interactions)
```

**Test Case Template**:
```python
class Test[FunctionName]:
    """
    Comprehensive tests for [function_name]
    Generated by brahma-test-generator
    """

    # Happy path
    def test_[function]_success(self):
        """Test [function] with valid inputs"""
        result = [function](valid_input)
        assert result == expected_output

    # Edge cases
    def test_[function]_empty_input(self):
        """Test [function] with empty input"""
        ...

    def test_[function]_boundary_value(self):
        """Test [function] at boundary (min/max)"""
        ...

    # Error cases
    def test_[function]_invalid_input_raises_error(self):
        """Test [function] raises error for invalid input"""
        with pytest.raises(ValueError):
            [function](invalid_input)

    # Property-based
    @given(st.text(), st.integers())
    def test_[function]_property(self, input1, input2):
        """Test [function] properties hold for any input"""
        result = [function](input1, input2)
        assert [property_to_verify]
```

### Phase 4: Test Quality Assessment

```markdown
**Quality Checklist**:

1. **Meaningful Assertions** (not just "no exception")
   - ❌ Bad: `assert result is not None`
   - ✅ Good: `assert result.status == 200 and result.user_id == 123`

2. **Descriptive Test Names**
   - ❌ Bad: `test_function_1()`
   - ✅ Good: `test_create_user_with_invalid_email_raises_value_error()`

3. **Independent Tests** (no shared state)
   - ✅ Each test sets up own data
   - ✅ Tests can run in any order
   - ✅ No global variables modified

4. **Readable & Maintainable**
   - ✅ Clear arrange-act-assert structure
   - ✅ Comments for complex setup
   - ✅ No code duplication (use fixtures)

5. **Fast Execution** (< 1 second per unit test)
   - ✅ Mock external services
   - ✅ Use in-memory database for tests
   - ✅ Avoid sleep() calls
```

**Test Quality Rubric** (1-100 score):

| Criteria | Weight | Scoring |
|----------|--------|---------|
| All tests pass | 25 | Pass: 25, Fail: 0 |
| Meaningful assertions | 20 | Good: 20, Partial: 10, Bad: 0 |
| Descriptive names | 15 | Good: 15, Partial: 8, Bad: 0 |
| Test independence | 15 | Independent: 15, Some deps: 8, Dependent: 0 |
| Readability | 10 | Clear: 10, OK: 5, Unclear: 0 |
| Execution speed | 10 | Fast (<1s): 10, Medium: 5, Slow: 0 |
| Coverage gain | 5 | ≥15%: 5, 5-15%: 3, <5%: 0 |

**Pass Threshold**: ≥ 70/100

### Python (pytest + Hypothesis)

```python
import pytest
from hypothesis import given, strategies as st
from src.api.users import create_user

class TestCreateUser:
    """
    Comprehensive tests for create_user function
    """

    # Fixture for test database
    @pytest.fixture
    def db(self):
        db = create_test_database()
        yield db
        db.cleanup()

    # Happy path
    def test_create_user_success(self, db):
        user = create_user(
            username="john",
            email="john@example.com",
            age=25
        )
        assert user.username == "john"
        assert user.email == "john@example.com"
        assert user.id is not None

    # Edge cases
    def test_create_user_minimum_age(self, db):
        user = create_user("user", "u@example.com", age=0)
        assert user.age == 0

    def test_create_user_maximum_age(self, db):
        user = create_user("user", "u@example.com", age=150)
        assert user.age == 150

    # Error cases
    def test_create_user_empty_username_raises_error(self, db):
        with pytest.raises(ValueError, match="Username required"):
            create_user("", "user@example.com", 25)

    def test_create_user_invalid_email_raises_error(self, db):
        with pytest.raises(ValueError, match="Invalid email"):
            create_user("john", "notanemail", 25)

    # Property-based tests
    @given(
        username=st.text(min_size=3, max_size=50),
        email=st.emails(),
        age=st.integers(min_value=0, max_value=150)
    )
    def test_create_user_property(self, db, username, email, age):
        """Any valid inputs should create user successfully"""
        user = create_user(username, email, age)
        assert user.username == username
        assert 0 <= user.age <= 150
```

```typescript
import { describe, it, expect, vi } from 'vitest';
import { fc } from 'fast-check';
import { processPayment } from './payment';

describe('processPayment', () => {
  // Happy path
  it('should process valid payment', async () => {
    const mockGateway = vi.spyOn(gateway, 'charge')
      .mockResolvedValue({ id: 'txn_123' });

    const result = await processPayment(100, 'USD', mockMethod);

    expect(result.success).toBe(true);
    expect(result.transactionId).toBe('txn_123');
  });

  // Edge cases
  it('should handle minimum amount', async () => {
    vi.spyOn(gateway, 'charge').mockResolvedValue({ id: 'txn' });
    const result = await processPayment(0.01, 'USD', mockMethod);
    expect(result.success).toBe(true);
  });

  // Error cases
  it('should reject negative amount', async () => {
    await expect(processPayment(-10, 'USD', mockMethod))
      .rejects.toThrow('Amount must be positive');
  });

  it('should handle gateway timeout', async () => {
    vi.spyOn(gateway, 'charge')
      .mockRejectedValue(new Error('Timeout'));

    const result = await processPayment(100, 'USD', mockMethod);
    expect(result.success).toBe(false);
  });

  // Property-based tests
  it('should handle any valid inputs', async () => {
    await fc.assert(
      fc.asyncProperty(
        fc.double({ min: 0.01, max: 1000000 }),
        fc.constantFrom('USD', 'EUR', 'GBP'),
        async (amount, currency) => {
          vi.spyOn(gateway, 'charge').mockResolvedValue({ id: 'txn' });
          const result = await processPayment(amount, currency, mockMethod);
          expect(result.success).toBe(true);
        }
      )
    );
  });
});
```

### Go (testing package)

```go
package users_test

import (
    "testing"
    "github.com/stretchr/testify/assert"
    "myapp/users"
)

func TestCreateUser_Success(t *testing.T) {
    user, err := users.Create("john", "john@example.com", 25)

    assert.NoError(t, err)
    assert.Equal(t, "john", user.Username)
    assert.Equal(t, "john@example.com", user.Email)
    assert.NotZero(t, user.ID)
}

func TestCreateUser_EmptyUsername_ReturnsError(t *testing.T) {
    _, err := users.Create("", "john@example.com", 25)

    assert.Error(t, err)
    assert.Contains(t, err.Error(), "username required")
}

func TestCreateUser_InvalidAge_ReturnsError(t *testing.T) {
    _, err := users.Create("john", "john@example.com", -1)

    assert.Error(t, err)
    assert.Contains(t, err.Error(), "invalid age")
}

// Table-driven tests (Go idiom)
func TestCreateUser_EdgeCases(t *testing.T) {
    tests := []struct {
        name      string
        username  string
        email     string
        age       int
        expectErr bool
    }{
        {"minimum age", "user", "u@example.com", 0, false},
        {"maximum age", "user", "u@example.com", 150, false},
        {"negative age", "user", "u@example.com", -1, true},
        {"excessive age", "user", "u@example.com", 200, true},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            _, err := users.Create(tt.username, tt.email, tt.age)
            if tt.expectErr {
                assert.Error(t, err)
            } else {
                assert.NoError(t, err)
            }
        })
    }
}
```

## Property-Based Testing Patterns

### Pattern 1: Idempotence
**Property**: Applying operation twice = applying once

```python
@given(st.text())
def test_lowercase_is_idempotent(s):
    """lowercase(lowercase(s)) == lowercase(s)"""
    assert s.lower().lower() == s.lower()
```

### Pattern 2: Inverse Operations
**Property**: Inverse operation reverses original

```python
@given(st.integers())
def test_negate_is_inverse(n):
    """negate(negate(n)) == n"""
    assert -(-n) == n
```

### Pattern 3: Invariants
**Property**: Certain properties always hold

```python
@given(st.lists(st.integers()))
def test_sort_preserves_length(lst):
    """sorted list has same length"""
    assert len(sorted(lst)) == len(lst)
```

### Pattern 4: Commutativity
**Property**: Order doesn't matter

```python
@given(st.integers(), st.integers())
def test_addition_is_commutative(a, b):
    """a + b == b + a"""
    assert a + b == b + a
```

### Pattern 5: Metamorphic Relations
**Property**: Output changes predictably with input

```python
@given(st.lists(st.integers()))
def test_reverse_twice_gives_original(lst):
    """reverse(reverse(lst)) == lst"""
    assert list(reversed(list(reversed(lst)))) == lst
```

### Pattern 2: Database Transaction Testing

```python
def test_transaction_rollback_on_error():
    """Test transaction rolls back on error"""
    try:
        with db.transaction():
            user = create_user('john', 'john@example.com', 25)
            # Force error
            raise Exception("Simulated error")
    except:
        pass

    # Verify user was NOT created (rollback worked)
    user = db.query(User).filter_by(username='john').first()
    assert user is None
```

### Pattern 3: Service Integration Testing

```python
def test_payment_service_integration():
```

## Best Practices

### DO:
✅ Focus on high-value tests (business logic, critical paths)
✅ Use property-based testing for pure functions
✅ Test edge cases (boundary values, null, empty)
✅ Make tests fast (< 1 second per unit test)
✅ Use descriptive test names
✅ Keep tests independent (no shared state)
✅ Mock external services (APIs, databases)

### DON'T:
❌ Test trivial code (getters, setters)
❌ Aim for 100% coverage wastefully
❌ Write brittle tests (testing implementation details)
❌ Use sleep() for timing (use proper async patterns)
❌ Ignore flaky tests
❌ Mix unit and integration tests
❌ Hardcode test data (use factories/fixtures)
